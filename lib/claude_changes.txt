SECTION 1: SECURITY — FIRESTORE RULES (PENDING)
==============================================================

--------------------------------------------------------------
THE PROBLEM
--------------------------------------------------------------
Current Firestore security rules:

  allow read, write: if request.auth.uid != null;

This means any Firebase-authenticated user — even one NOT on
the member list — can:

  - Read every member's name, phone, address, family info
  - Delete any announcement
  - Edit any member's document
  - Set isAdmin: true on their own account

The Flutter client-side membership and admin checks are UI
gatekeeping only. Firestore rules are the ONLY server-side
protection. The rules must be fixed.

--------------------------------------------------------------
THE SOLUTION: memberEmails Collection
--------------------------------------------------------------
Create a new Firestore collection called `memberEmails` where
each document ID is the member's email address.

  memberEmails/john@gmail.com   →  { isAdmin: false }
  memberEmails/admin@gmail.com  →  { isAdmin: true }

This allows Firestore rules to verify membership using
  request.auth.token.email
from the Firebase auth token — no document ID migration needed.

WHY NOT use Firebase UID as document ID?
  - Admins create member records before members register
    (UID is unknown at creation time)
  - Would require migrating 500 existing documents
  - More complex email-change flow

--------------------------------------------------------------
FINAL FIRESTORE SECURITY RULES
--------------------------------------------------------------
Apply these in: Firebase Console → Firestore → Rules

  rules_version = '2';
  service cloud.firestore {
    match /databases/{database}/documents {

      match /memberEmails/{email} {
        // Readable pre-verification: app checks this BEFORE
        // email verification during new user registration.
        // memberEmails only contains { isAdmin: bool } so
        // exposing it pre-verification is safe.
        allow read:  if request.auth != null;
        allow write: if isAdmin();
      }

      match /membersPublic/{docId} {
        allow read:           if isMember();
        allow update:         if isMember()
                               && resource.data.uid == request.auth.uid;
        allow create, delete: if isAdmin();
      }

      match /announcements/{announcementID} {
        allow read:  if isMember();
        allow write: if isAdmin();
      }
    }
  }

  function isAuthenticated() {
    return request.auth != null
        && request.auth.token.email_verified == true;
  }

  function isMember() {
    return isAuthenticated()
        && exists(/databases/$(database)/documents/memberEmails/$(request.auth.token.email));
  }

  function isAdmin() {
    return isMember()/b
        && get(/databases/$(database)/documents/memberEmails/$(request.auth.token.email)).data.isAdmin == true;
  }

WHAT THIS FIXES:
  - Non-member with Firebase account reads directory     ✅
  - Non-member writes/deletes announcements              ✅
  - Member edits another member's document               ✅
  - User self-elevates isAdmin in membersPublic          ✅
    (admin gate reads from memberEmails, not membersPublic)
  - Removed member retains access                        ✅
    (delete their memberEmails entry = instant lockout)
  - Unauthenticated access                               ✅

--------------------------------------------------------------
STEP 1: MIGRATE EXISTING 500 MEMBERS
--------------------------------------------------------------
Do NOT do this manually in the Firebase Console.
Use a one-time Node.js migration script.

IMPORTANT: Take a Firestore backup first.
  Firebase Console → Firestore → Import/Export → Export

STEP 1 — Install dependencies (one time):
  npm install firebase-admin

STEP 2 — Download service account key:
  Firebase Console → Project Settings → Service Accounts
  → Generate new private key → save as serviceAccount.json

STEP 3 — Create migrate.js:

  const admin = require('firebase-admin');
  const serviceAccount = require('./serviceAccount.json');

  admin.initializeApp({
    credential: admin.credential.cert(serviceAccount)
  });

  const db = admin.firestore();

  async function migrate() {
    const snapshot = await db.collection('membersPublic').get();
    const batch = db.batch();
    let count = 0;

    snapshot.forEach(doc => {
      const data = doc.data();
      // Migrate ALL documents that have an email — not just
      // accountExists=true. memberEmails is the approved member
      // list for BOTH existing accounts AND future registrations.
      // Filtering by accountExists would break registration for
      // members who haven't signed up yet.
      if (data.email) {
        const ref = db.collection('memberEmails').doc(data.email);
        batch.set(ref, { isAdmin: data.isAdmin === true });
        count++;
      }
    });

    await batch.commit();
    console.log(`Migrated ${count} members (${snapshot.size} total docs scanned).`);
  }

  migrate().catch(console.error);

STEP 4 — Run it:
  node migrate.js

STEP 5 — Verify in Firebase Console that memberEmails
  collection has ~500 documents, then apply the new rules.

STEP 2: FIX AUTH FLOW CONFLICT (code change needed)
--------------------------------------------------------------
FILE: lib/services/verify_user.dart — verifyEmail()

The current verifyEmail() queries membersPublic to check if the
user's email exists. Under the new rules, membersPublic requires
email_verified=true to read. But verifyEmail() is called BEFORE
the user verifies their email — so the read would be blocked.

FIX: Change verifyEmail() to check memberEmails/{email} directly
instead of querying membersPublic.

  BEFORE (queries membersPublic):
    QuerySnapshot result = await FirebaseFirestore.instance
        .collection('membersPublic')
        .where('email', isEqualTo: email)
        .get();
    return result.docs.isNotEmpty;

  AFTER (direct doc lookup on memberEmails):
    DocumentSnapshot doc = await FirebaseFirestore.instance
        .collection('memberEmails')
        .doc(email)
        .get();
    return doc.exists;

This is also faster (direct lookup vs. collection query).

--------------------------------------------------------------
STEP 3: KEEP memberEmails IN SYNC GOING FORWARD (code changes)
--------------------------------------------------------------
memberEmails must stay in sync with membersPublic in 3 situations:

  1. Admin adds a new member
       → create membersPublic doc AND memberEmails/{email}
       File: lib/services/access_data.dart — addDocument()

  2. Admin changes a member's email
       → delete memberEmails/{oldEmail}
       → create memberEmails/{newEmail}
       Files: lib/services/search_helper.dart — submitChanges()
              lib/screens/home/admin/edit_user_info.dart — submitUserChanges()

  3. Admin changes admin status
       → update memberEmails/{email}.isAdmin
       File: lib/services/search_helper.dart — submitChanges()
